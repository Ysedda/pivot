# 1.1 Reinstall Proxmox myself

**Goal:** wipe the fast-mode install and rebuild the host from the ISO, so that every line in `/etc/network/interfaces` is one I chose and can defend. Decisions go in [lab/README.md](../lab/README.md#decisions).

## Read

- Proxmox admin guide, [Host System Administration → Network Configuration](https://pve.proxmox.com/pve-docs/pve-admin-guide.html#sysadmin_network_configuration): read the "Masquerading (NAT) with iptables" part twice.
- Proxmox admin guide, [Logical Volume Manager](https://pve.proxmox.com/pve-docs/pve-admin-guide.html#chapter_lvm) and [ZFS on Linux](https://pve.proxmox.com/pve-docs/pve-admin-guide.html#chapter_zfs): the intro and the hardware/RAM requirements only.
- Arch wiki, [wpa_supplicant](https://wiki.archlinux.org/title/Wpa_supplicant): the configuration and "Connecting with wpa_passphrase" sections. Ignore the Arch-specific service bits; Proxmox uses ifupdown2.

## Exercises (on the current install, before wiping)

1. `ip -br addr`, `ip route`, `bridge link`: draw the host's interfaces and routes on paper. Which interface owns the default route?
2. `cat /proc/sys/net/ipv4/ip_forward`. Set it to `0` at runtime, ping `1.1.1.1` from a guest, then set it back. What broke, and why didn't the host's own traffic break?
3. `nft list ruleset` (or `iptables -t nat -S`): find the masquerade rule. Which chain and hook is it on, and why that one rather than prerouting?
4. `wpa_passphrase <ssid>`: what does it output, and why is a PSK hash in a file not much safer than the plaintext?
5. `lvs`, `vgs`, `pvs`: what is `data` and why is it "thin"? What happens when a thin pool hits 100%?

## Build

- Fresh install from the ISO, Wi-Fi up with `wpa_supplicant` from `/etc/network/interfaces`, static `192.168.1.50`.
- `vmbr0` with no physical port, `10.10.10.1/24`, forwarding and masquerade persistent across reboot.
- No-subscription repository, `apt full-upgrade`, one guest reaching the internet.
- Every choice written under "Decisions" in `lab/README.md`.

## Break it

- Reboot and check that everything came back by itself (forwarding, NAT, Wi-Fi).
- Remove the masquerade rule and predict what a `tcpdump -i wlo1` shows when a guest pings out. Then check.

## You should be able to explain

- Why bridging guests onto the LAN fails over Wi-Fi (the 3-address frame / one-MAC-per-association limit).
- What `ip_forward` does and what MASQUERADE rewrites, on the way out and on the way back (conntrack).
- LVM-thin vs ZFS for 15 GB of RAM on one NVMe, and which one you picked.
