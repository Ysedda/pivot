# 1.2 Incident: the host keeps dropping off the network

**Goal:** find out from the evidence why the host disappears, fix it, and write [postmortem #1](../../postmortems/). The reading below teaches you how to dig, not what you'll find.

## Read

- `man journalctl`: `--list-boots`, `-b`, `-k`, `-p`, `-u`, `--since/--until`, `-o short-precise`.
- Google SRE book, [ch. 15 Postmortem Culture](https://sre.google/sre-book/postmortem-culture/): what a blameless postmortem contains and why.

## Exercises (on any Linux box, before touching the incident)

1. `journalctl --list-boots`: how many boots does the journal keep, and where is that configured? Is the journal persistent on this host (`/var/log/journal` vs `/run/log/journal`)? Why does that matter for this incident?
2. Show only warnings and above from the previous boot, kernel messages only. Then only the last 5 minutes before that boot ended.
3. `journalctl -u systemd-logind -b` and `journalctl -u NetworkManager` (or `wpa_supplicant`): what does each unit log when nothing is wrong? You need the baseline to spot the anomaly.
4. `iw dev`, `iw dev <if> link`, `iw dev <if> get power_save`: what does each tell you?
5. Write down the timeline format you'll use (UTC timestamps, what happened, how you knew) before you start the investigation.

## Build

- Reproduce the drop on purpose, at least once, while watching `journalctl -f` from another machine's SSH session or the console.
- Root cause(s) found from logs, fixed persistently, verified by surviving the trigger again.
- Postmortem written: timeline, detection, mitigation, root cause, what changes.

## Break it

The incident is the breakage. After the fix, trigger it again and prove the host stays up.

## You should be able to explain

- How you narrowed it down: which log line was the evidence, and what you ruled out first.
- Why each fix holds across a reboot.
- The difference between mitigation and root-cause fix in your own timeline.
