# 1.5 Troubleshooting method

**Goal:** a repeatable method for "the box is slow / something's wrong", run the same way every time, fast.

## Read

- Brendan Gregg, [The USE Method](https://www.brendangregg.com/usemethod.html): the method and the Linux checklist.
- Netflix Tech Blog, [Linux Performance Analysis in 60,000 Milliseconds](https://netflixtechblog.com/linux-performance-analysis-in-60-000-milliseconds-accc10403c55): the 10 commands, in that order.
- `man 5 proc`: `/proc/loadavg`, `/proc/meminfo`, `/proc/pressure/*` (PSI).

## Exercises (idle box first, so you know normal)

1. Run the 60-second checklist on an idle VM and save the output. That's your baseline.
2. `uptime` shows load 4.0 on 4 CPUs: is the box saturated? What else counts in Linux load besides runnable tasks?
3. `vmstat 1`: which columns are CPU saturation (`r`), memory pressure (`si/so`), I/O wait (`wa`)? Run `stress-ng --cpu 8 --timeout 30s` on a smaller VM and watch them move.
4. `free -h`: why is low "free" fine and what number actually matters?
5. `iostat -xz 1`: what are `%util` and `aqsz`, and why can `%util` mislead on NVMe?
6. `cat /proc/pressure/{cpu,memory,io}`: read `some` vs `full`.
7. Write your own one-page USE checklist (CPU, memory, disk, network × U/S/E) with the command for each cell. That card is the deliverable of the exercises.

## Build

- Your checklist in `tips.md` (or linked from it).
- A drill VM sized small enough that `stress-ng` hurts it.

## Break it (Claude breaks, you find it, timed)

Four drills, one at a time, without being told which: CPU hog, memory leak to OOM kill, disk full, I/O saturation. Record time-to-diagnosis for each.

## You should be able to explain

- USE: utilization vs saturation vs errors, with one example per resource.
- How you'd tell an OOM kill happened, after the fact (`dmesg`, `journalctl -k`, exit 137).
- Why load average alone can't tell CPU-bound from I/O-bound.
