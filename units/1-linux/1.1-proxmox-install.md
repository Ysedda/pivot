# 1.1 Reinstall Proxmox myself

**Goal:** wipe the fast-mode install and rebuild the host from the ISO, so that every line in `/etc/network/interfaces` is one I chose and can defend. Decisions go in [lab/README.md](../../lab/README.md#decisions).

## Theory

### 1. What Proxmox actually is

Proxmox VE is **Debian with a hypervisor stack and a management layer on top**. Nothing magic:

| Layer | What it is | What you touch |
| --- | --- | --- |
| KVM | A kernel module (`kvm_intel`) that uses the CPU's VT-x to run guest code directly on the CPU | `lsmod \| grep kvm` |
| QEMU | A userspace process per VM that emulates the hardware around the CPU: disks, NICs, BIOS | `ps aux \| grep kvm`: one process per running VM |
| LXC | Containers (namespaces + cgroups, block 3) sharing the host kernel | `pct` |
| Proxmox services | `pvedaemon`, `pveproxy` (web UI on :8006), `pve-cluster` (config in `/etc/pve`, a FUSE filesystem backed by SQLite) | `qm`, `pvesm`, web UI |

So "a VM" is a QEMU process. Killing that process is pulling the power cord on the VM. Everything you know about Linux processes (1.3) and systemd (1.4) applies to the host.

### 2. How Debian configures the network

Proxmox uses **ifupdown2**. The whole network config is one file, `/etc/network/interfaces`:

```
auto wlo1                      # bring it up at boot
iface wlo1 inet static         # IPv4, fixed address
    address 192.168.1.50/24
    gateway 192.168.1.254
```

`ifreload -a` applies changes without a reboot. ifupdown2 diffs the file against the current state and only touches what changed. `ip addr` / `ip route` show the **runtime** state. The file is the **desired** state. When they disagree, someone ran `ip` by hand and it won't survive a reboot. Desired vs actual state is the same idea as Kubernetes and OpenTofu later.

### 3. Wi-Fi: who does what

```
wpa_supplicant  (userspace: authentication, WPA2 4-way handshake, roaming)
      │  nl80211 (netlink API)
cfg80211 / mac80211  (kernel Wi-Fi stack)
      │
driver + firmware  (the actual radio)
```

The interface `wlo1` exists as soon as the driver loads, but it carries nothing until `wpa_supplicant` has **associated** with the access point and finished the handshake. With ifupdown you hand it the credentials in the interfaces file (`wpa-ssid` / `wpa-psk`) or point at a config file (`wpa-conf`), and ifupdown starts `wpa_supplicant` for you.

`wpa_passphrase` turns the passphrase into the 256-bit PSK (PBKDF2 of the passphrase, salted with the SSID). Having the PSK in the file instead of the passphrase hides the human-readable password. But **the PSK is enough to join that network**, so the file still has to be `0600 root`.

### 4. Why guests can't just sit on the home LAN

On a wired host you'd make `vmbr0` a bridge containing the physical NIC. Guests would then be ordinary machines on 192.168.1.0/24, each with its own MAC address. Over Wi-Fi this breaks:

- In normal (infrastructure) mode, a station talks to the AP with **3-address frames**: AP, sender, final destination. The sender has to be the MAC that associated. A guest's frame has the guest's MAC as sender, and the AP has no association for that MAC, so it drops the frame.
- On the way back, the AP only delivers frames to MACs it has associated, so replies addressed to the guest's MAC never arrive.
- 4-address mode (WDS) fixes this, but it needs AP support that home routers rarely expose.

So the host has to **route** for the guests instead of **bridging** them. That's a layer 3 fix for a layer 2 limit.

### 5. The design: a private switch, a router and NAT

```
guest 10.10.10.20 ──tap── vmbr0 (10.10.10.1) ══ host routing ══ wlo1 (192.168.1.50) ── router .254 ── internet
                        [ L2: virtual switch ]   [ L3: forward + NAT ]
```

**The bridge (`vmbr0`)** is a software L2 switch in the kernel. Each VM's virtual NIC shows up on the host as a `tap` interface plugged into the bridge. With `bridge-ports none` the switch has no uplink, so it's a private network. Giving the bridge itself `10.10.10.1` puts the host on that network, and the guests use it as their default gateway.

**Forwarding (`ip_forward`).** By default Linux drops any packet that isn't addressed to one of its own IPs. `net.ipv4.ip_forward = 1` turns the host into a router: a packet coming in on `vmbr0` for 1.1.1.1 gets looked up in the routing table and sent out the default route (`wlo1`). It's a runtime kernel setting (`/proc/sys/...`). Persist it in `/etc/sysctl.d/` or with a `post-up` line, or it's gone at reboot.

**NAT (MASQUERADE).** Forwarding alone isn't enough. The guest's packet leaves with source `10.10.10.20`. The home router has no route to 10.10.10.0/24, and the internet will never route a private address back, so replies go nowhere. Source NAT rewrites the source to the host's own address (`192.168.1.50`) as the packet leaves:

- It happens in the **postrouting** hook because that runs *after* the routing decision. Only then does the kernel know the packet is leaving via `wlo1` and which source address fits that interface.
- **MASQUERADE** is SNAT to "whatever address the outgoing interface has right now". It's for interfaces whose IP can change. With a static IP, plain `snat to 192.168.1.50` does the same thing slightly cheaper.
- **conntrack** records each translation (`10.10.10.20:51234 ↔ 192.168.1.50:51234 → 1.1.1.1:53`). Replies match that entry and get rewritten back to the guest automatically. You never write a rule for the return path.
- Consequence: **inbound** connections from the LAN have no conntrack entry, so nothing reaches a guest unless you add a DNAT (port forward), or a static route on the LAN side via `192.168.1.50`.

**One packet, start to finish** (guest pings 1.1.1.1):

1. The guest's routing table says "default via 10.10.10.1". ARP finds the bridge's MAC, and the frame goes out the tap into `vmbr0`.
2. The host receives it on `vmbr0`. The destination isn't local, `ip_forward=1`, and the route lookup picks `wlo1`.
3. Postrouting: the masquerade rule rewrites the source to 192.168.1.50, and conntrack stores the mapping.
4. Out via Wi-Fi as the host's own MAC and IP. The AP is happy.
5. The reply arrives at 192.168.1.50. Conntrack recognizes it and rewrites the destination back to 10.10.10.20, then forwards it out `vmbr0` to the guest.

If you can tell this story on a whiteboard, you understand most of what Kubernetes Service networking does in block 4 (it's DNAT + conntrack again).

> The Proxmox firewall adds its own bridges and conntrack handling, and the docs warn that NAT can break when it's enabled (they give a conntrack-zone workaround). Leave the PVE firewall off for this unit and know the caveat exists.

### 6. Storage: LVM-thin vs ZFS

**LVM** stacks three layers: **PV** (a disk or partition) → **VG** (a pool of PVs) → **LV** (a slice of the pool that acts like a disk). A normal ("thick") LV reserves all its space up front.

**LVM-thin**: one big LV becomes a *thin pool*, and VM disks are *thin volumes* inside it that only use blocks when written. You can promise 3 VMs 100 GB each on a 200 GB pool (overprovisioning), and snapshots are cheap. The catch: **if the pool hits 100%, writes fail and guests get I/O errors or freeze.** Watch `Data%` and `Meta%` in `lvs`.

**ZFS** is a filesystem and volume manager in one: checksums on every block, built-in compression, snapshots and send/receive, copy-on-write. It caches in RAM (the **ARC**). Proxmox ≥ 8.1 caps the ARC at 10% of RAM on new installs, but ZFS still wants memory and CPU headroom.

For this box: **one NVMe, no mirror**, so ZFS can *detect* corruption but can't *repair* it, and you'd pay RAM out of the 15 GB that block 4 and 7 need. LVM-thin is leaner. ZFS gives compression, better snapshots and something to talk about. Pick one and write the reason down. Either answer is fine if you can defend it.

### 7. Repositories

The installer configures the **enterprise** repo, which needs a paid subscription and makes `apt update` fail without one. For a lab you switch to **pve-no-subscription**, which gets the same packages a little earlier and with less testing. Proxmox 9 sits on Debian 13 and uses the deb822 `.sources` format under `/etc/apt/sources.list.d/`. Read the files the installer created before you change anything.

## Exercises (on the current install, before wiping)

1. `ip -br addr`, `ip route`, `bridge link`: draw the host's interfaces and routes on paper. Which interface owns the default route?
2. `cat /proc/sys/net/ipv4/ip_forward`. Set it to `0` at runtime, ping `1.1.1.1` from a guest, then set it back. What broke, and why didn't the host's own traffic break?
3. `nft list ruleset` (or `iptables -t nat -S`): find the masquerade rule. Which chain and hook is it on, and why that one rather than prerouting?
4. `wpa_passphrase <ssid>`: what does it output, and why is a PSK hash in a file not much safer than the plaintext?
5. `lvs`, `vgs`, `pvs`: what is `data` and why is it "thin"? What happens when a thin pool hits 100%?
